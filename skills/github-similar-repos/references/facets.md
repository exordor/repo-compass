# Facet taxonomy and query-writing notes

Read this when a repo is hard to decompose, or when a facet's searches keep returning the wrong kind of thing.

## The five facet types, with examples

### Intent — what problem, for whom

The user-facing purpose. Phrase it the way the author's target audience would describe their need, not the way the code is organised.

| Repo | Intent facet | Query that works |
|---|---|---|
| mg-styles-15 | make motion-design videos by having an AI write code | `motion graphics generated by Claude Code` |
| nanoGPT-style repo | train a small GPT from scratch for learning | `minimal GPT training from scratch educational github` |
| an Obsidian plugin that syncs to Notion | keep notes in two tools without manual copying | `obsidian notion sync plugin` |

Weak query: the repo's own tagline verbatim. Marketing phrases are unique to one README; the *need* is shared across many.

### Technical route — how it does it

Comes mostly from manifests and the file tree. The route is often more shareable than the intent: a dozen unrelated projects may use the same headless-browser-to-video pipeline.

| Signal in repo | Route facet | Query |
|---|---|---|
| `puppeteer` / `playwright` in package.json + ffmpeg mentioned | headless Chrome frame capture → ffmpeg | `headless chrome capture frames ffmpeg video` |
| `torch`, `transformers`, `peft` in requirements | LoRA fine-tuning of HF models | `lora fine-tuning transformers peft script github` |
| `index.html` + no bundler + `three` via CDN | single-file Three.js demo | `single file three.js demo no build` |

When the route is a well-known framework (Remotion, Next.js, PyTorch Lightning), the peers are *other projects on that framework*, not the framework itself. Query for the use-case plus the framework name.

### Output form — what kind of artefact it is

This decides who would actually use the repo and how, so mismatches here feel wrong to users even when the topic matches. Common forms:

- library / SDK
- CLI tool
- agent skill or plugin (Claude Code skill, Cursor rule, MCP server)
- showcase / gallery / portfolio (works + how they were made)
- prompt collection or template library
- dataset
- benchmark / eval harness
- paper reproduction
- tutorial / course / book-as-repo
- awesome-list (curated links)
- template / starter / boilerplate

Query pattern: `<topic> <form word>`, e.g. `motion design prompts collection`, `awesome claude code skills`, `diffusion paper reproduction pytorch`.

### Ecosystem — where it lives

The platform, community, or distribution channel. Matching here finds things the user can *install alongside* or *swap for* the original.

Examples: Claude Code skills, VS Code extensions, HuggingFace Spaces, Obsidian plugins, Home Assistant integrations, Neovim plugins, ComfyUI custom nodes, ROS packages, Hugo themes.

Query: the ecosystem's own vocabulary plus the topic — `comfyui custom node video interpolation`, `neovim plugin lsp inlay hints`. Also try `awesome <ecosystem>`.

### Signature — the one unusual thing

The detail you'd mention first when describing the repo to a friend. It is rarely in the tagline and often buried in the README body or the file tree.

| Repo | Signature | Why it matters |
|---|---|---|
| mg-styles-15 | the soundtrack is synthesised by Python code, not sourced | the few other repos that do this are the closest matches overall |
| a dotfiles repo | every config is generated from one Nix flake | separates it from 100k ordinary dotfiles repos |
| a model-training repo | trains on a single consumer GPU in under an hour | peers are "cheap/fast training" repos, not "same architecture" repos |

Searching the signature usually returns few results, and that's the point: the ones it does return are high-value.

## Query-writing rules of thumb

1. Use nouns a matching README would contain. The search engine matches text; the facet label is your abstraction, not theirs.
2. 3–7 words. Add `github` unless the engine is already scoped to it.
3. One query per angle. "Same angle, reworded" returns the same page.
4. If results are all huge frameworks, add a form word (`skill`, `demo`, `example`, `minimal`) to drop down to peer-sized projects.
5. If results are all blog posts, add `github` or `repo` and drop how-to words like "tutorial", "guide".
6. `awesome <topic>` is cheap and often returns a curated list you can mine for ten candidates at once.

## Dedup and grouping

- A candidate found by two facets' queries is a strong signal; count both.
- Same author's other repos: one small group at the end, never mixed into the main list.
- Forks: skip unless the fork has clearly diverged (different README, many commits ahead).
- Archived or no commits in 3+ years: mention only if nothing else exists for that facet, and say so.
