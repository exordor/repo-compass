name: github-similar-repos
description: Facet-based recommendation and positioning for any GitHub repo. Given a URL or owner/repo, decompose it into facets (problem, technical route, output form, ecosystem, distinctive signature), search each facet separately, verify candidates, and return repos grouped by shared facet with a one-line "what matches / what differs" each, plus the repo's upstream, downstream, health numbers and evidence-based alternatives. Use whenever the user asks for repos "like", "similar to", "alternatives to" or "related to" one, pastes a GitHub link and asks what else exists, or complains that Trending/Explore doesn't surface what they want. Also use when they just discovered a repo (tweet, post, newsletter) and ask whether it's worth using, what it's built on, who builds on it, or whether a more mature alternative exists. # GitHub similar-repo recommendation

GitHub has no real "related repositories" feature. Trending ranks by star velocity, Topics is a flat tag bag, and the dashboard feed is sparse. The gap this skill fills: given one repo, find the repos a knowledgeable person in that niche would point you to, including small ones with a few dozen stars, and explain *why* each one is related.

The core idea: a repository is never just one thing. A single repo can simultaneously be "a showcase of AI-generated motion design", "a headless-Chrome-to-ffmpeg render pipeline", "a style prompt library" and "a make→review→revise workflow example". A single nearest-neighbour search collapses all of that into one blurry "most similar overall" list, which is usually dominated by the same author's other repos. Searching along each facet separately, then grouping results by facet, is what makes the output useful.

## Workflow

### 1. Read the repo as several things at once

Fetch, in parallel where possible:

- The README. Try `https://raw.githubusercontent.com/<owner>/<repo>/HEAD/README.md` first (clean text); fall back to the repo page `https://github.com/<owner>/<repo>` which also gives description, topics, stars, language, last commit, and the top-level file list.
- Dependency manifests, based on what the file list shows: `package.json`, `requirements.txt`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `environment.yml`, etc., via `raw.githubusercontent.com`. Dependencies are the most honest technical-stack signal a repo has: the author wrote them for the machine, not for marketing.
- If the README is thin, look at one or two directory names or a key source file. Directory structure often reveals the output form (`prompts/`, `skills/`, `benchmark/`, `notebooks/`, `demos/`).

Non-English READMEs are fine; read them as they are.

### 2. Decompose into facets

Write down 3–6 facets. Each facet is a *distinct* answer to "what is this repo?" — if two facets would pull the same candidates, merge them. See `references/facets.md` for the facet taxonomy with examples, but the usual ones are:

| Facet type | The question it answers |
|---|---|
| Intent | What problem does it solve, for whom? |
| Technical route | What stack, architecture, or pipeline does it use? (from manifests + README) |
| Output form | Is it a library, CLI, agent skill, showcase/gallery, dataset, benchmark, tutorial, paper reproduction? |
| Ecosystem | Which platform or community does it live in? (Claude Code skills, HuggingFace, Remotion, ROS, Obsidian plugins…) |
| Signature | The one unusual choice that makes it recognisable — the thing you'd mention first when describing it to a friend. |

The **signature** facet is the most valuable and the easiest to skip. For mg-styles-15 the signature was "the soundtrack is also generated by code"; candidates sharing that one detail turned out to be the closest matches overall. Always look for it.

For each facet, write 1–3 search queries. Good queries use the concrete nouns a *matching README would contain*, not the abstract facet name: "headless chrome capture frames ffmpeg" finds renderers; "video rendering tool" finds nothing useful. Add `github` to the query. For the ecosystem facet, searching `awesome <topic>` often surfaces a curated list that is itself a candidate and a pool of further candidates.

### 3. Search each facet separately

Run the queries. Send them in the same turn so they run in parallel. Keep a running candidate list with: name, URL, one-line description, and which facet's query found it.

Don't stop at the first page of one query. A facet whose queries return only mega-projects (frameworks with 50k stars) usually needs a more specific query; a facet whose queries return nothing may be too narrow, so widen it once. Two rounds per facet is normal; five is too many.

### 4. Verify and characterise candidates

Verify every candidate you intend to recommend. This is non-negotiable because search snippets lie by omission: a repo can look like a match from one sentence and turn out to be a fork, abandoned, a tutorial about the thing rather than the thing, or the same author's sibling project.

The cheapest reliable check is the JSON endpoint `https://api.github.com/repos/<owner>/<repo>`. One fetch gives `full_name` (follows renames and transfers, so you learn the repo moved), `description`, `stargazers_count`, `language`, `fork`, `archived`, `pushed_at` (real last activity; the HTML page often doesn't render it), and `topics`. Fall back to the HTML page only when you also need README content to judge the match. Note:

- Exists, is not a fork, is not archived, has real content (not an empty scaffold).
- Description, stars, language, `pushed_at`.
- Which of *your* facets it actually shares, and the one thing it does differently.

Search results for skill, plugin and prompt ecosystems are often registry mirror pages (skill marketplaces, "awesome" aggregators with their own domains) rather than GitHub. Resolve those back to the GitHub repo they describe before verifying; adding `github` to the query usually avoids them in the first place.

Drop candidates that only match on a word. Set aside same-author repos into their own small group rather than letting them dominate.

Upstream frameworks (Remotion to a Remotion-based project, PyTorch to a model repo) are worth one line as "the framework this sits on" but are not peer recommendations unless the user is asking about the stack itself.

### 4b. Position the repo: upstream, downstream, alternatives

People often arrive at a repo from a social-media post, not from a search. What they need then is not "more like this" but "where does this sit, and is it the one to use?". Three questions answer that; gather the evidence while you verify candidates, since it comes from the same API responses.

**Upstream — what it builds on.** Read it off the manifests and README: the framework it's written in, the model or weights it wraps, the library doing the heavy lifting (a "local LLM runner" that is a Go wrapper around llama.cpp; a "PPT skill" that is a prompt around PptxGenJS). Name the one or two that matter. This tells the user whether the repo is infrastructure or a convenience layer over someone else's infrastructure, which decides how much they should depend on it.

**Downstream — what builds on it.** Search `"<repo name>" port|plugin|integration|based on|fork`, and look at the README's "integrations" or "community" section if it has one. Ports to other languages, UIs built on its API, and diverged forks all count. A repo with a real downstream has a community that will keep it alive; a repo with none is a bet on its author.

**Alternatives — and which is better for what.** These are the candidates that do the *same job* (same intent + same output form), as opposed to merely sharing a facet. Include the original itself in the `scripts/repo_health.py` run (step 5) so its row sits next to theirs. The columns to read for the verdict:

- stars/day since creation. A repo at 20k stars after 30 days and one at 20k stars after 5 years are different objects; the first is a launch, the second is an institution. Say which the original is.
- days since last push → maintained or not. Over six months quiet is worth stating.
- issue close rate and PR merge rate → whether the maintainers answer.
- ARCHIVED, FORK, license.

Then write one plain sentence per alternative on what it is better *for* — more mature, more maintained, lighter, broader, better documented, different trade-off — grounded in those numbers and the READMEs, not in general reputation. If the original is clearly the best choice for its job, say so; "the hyped one is also the best one" is a legitimate and useful finding. If it is a thin wrapper and the upstream is what the user actually wants, say that too.

### 5. Rank: relevance first, health second

Ranking has two layers, and the order matters.

**Relevance tier** is your judgment and comes first. Tier 3: shares three or more facets, or does the exact same job. Tier 2: shares two facets. Tier 1: shares one. Nothing in the health data moves a repo between tiers — a 40-star repo on the exact same route stays above a 10k-star repo in the general area, or the output degenerates into Trending.

**Health score** orders repos *within* a tier and tells the user whether they can depend on it. Run the bundled script once with every verified candidate, passing the tiers you assigned:

```
python scripts/repo_health.py \
  --tier "3:owner/a,owner/b" --tier "2:owner/c" --tier "1:owner/d,owner/e"
```

It fetches `api.github.com` for each repo and prints one table sorted by tier, then score, with the columns that produce the score: stars and stars/day since creation, age, days since last push, issue close rate, PR merge rate, whether it has releases, license, and ARCHIVED / FORK / moved flags. The score weights recency most (35%), then traction (25%, log-scaled stars so 100k-star projects don't drown everything), maintenance (25%, close and merge rates) and maturity (15%). `--json` gives the same data for your own use. The script needs a shell that can reach `api.github.com` (your own machine normally can; some cloud sandboxes cannot). When it fails, use WebFetch instead: `https://api.github.com/repos/<owner>/<repo>` for each candidate, or `https://ungh.cc/repos/<owner>/<repo>` (a public mirror of the same core fields) if that endpoint is blocked too, and compute the two numbers that matter most by hand: days since `pushed_at`, and `stargazers_count` divided by days since `created_at`.

Why these signals and not raw stars: star count rewards age and virality equally, so it is read together with stars/day; `open_issues_count` from the repo endpoint silently includes open PRs, so the script counts issues and PRs separately via the search API; a large open-issue count is ambiguous (popular or neglected) while the close rate is not; and the most recent push is the single hardest fact about whether anyone is home.

Put the health columns in the output next to each repo (at least stars, ★/day, last push), so the user sees the evidence rather than only the score. The score is a summary of the columns, not a verdict; use it to order, and use the columns to explain.

### 6. Write the output

The explanations *are* the product. A list of names without "why" is what GitHub already gives you.

Match the user's language. Use this structure:

```
**定位 / Positioning** (one short paragraph): what the repo is, the facets you found, and its health line — "created <when>, ★N (~M/day), last push <when>, <open issues>, <license>". Then one sentence on where it sits: built on <upstream>; <downstream> builds on it (or: no visible downstream yet).

**替代 / Alternatives — same job, different trade-offs**
- owner/repo (★N, created <when>, last push <when>) — what it is. Better for: <one grounded reason>. The original is better for: <one grounded reason>.
(2–4 entries. End with one sentence of verdict: which to pick for which situation, or that the original is the right pick.)

**Closest — share most facets**
- owner/repo (★N) — what it is in one line. Shares: X, Y, Z. Differs: W.

**Same <facet A>** / **Same <facet B>**
- …

(Optional) **Upstream / Downstream** — one line each where not already covered above. **Same author** — one line each.

Closing: one observation at the pattern level if there is a real one — e.g. "most of these appeared in the last three months and have under 100 stars, which is why Trending won't show them". Skip it if there isn't one.

Sources: markdown links to every repo mentioned.
```

Lead with positioning and alternatives because that is the decision the user is usually making; the facet groups are the supporting evidence. When the user explicitly asks only for "similar" repos and shows no sign of evaluating the original, the positioning paragraph can shrink to its health line and the alternatives group can merge into "Closest".

Keep each recommendation to one or two lines. Cap the list at 12 recommendations, including the same-author and framework groups; past that it stops being a recommendation and becomes a search results page, and the user loses the ability to act on it. Every test so far has found a reason to go over ("this facet is unusually crowded") and the reason is always true — crowded facets are the norm, not the exception. The fix is to cut, not to explain: keep the two or three most specific matches per facet, name the awesome-list or topic page where the rest live, and move on. If the user wants depth or breadth on one facet, they'll ask.

## What good looks like

For `Vincentwei1021/mg-styles-15` (15 motion-design films generated by Claude writing code; HTML/Canvas rendered via headless Chrome + ffmpeg; soundtrack synthesised in Python; prompts + source + rubric included), the facets were: AI-writes-code motion design (intent), headless-Chrome→ffmpeg pipeline (route), showcase-with-prompts (form), Claude Code skill ecosystem (ecosystem), code-generated audio (signature). The output grouped a Claude Code motion skill that also generates its own soundtrack as "closest", three more motion-graphics skills under the intent facet, a curated "awesome Claude video" list under form, two headless-Chrome renderers plus Remotion/Motion Canvas under route, and two UI-style prompt libraries under the "style × prompt collection" form. Each line said what matched and what didn't.

## Pitfalls

- Recommending from memory without fetching. Many of the best matches are weeks old and have double-digit stars; they are not in training data. Search and verify.
- Letting one facet eat the list. If every result is a renderer, the intent facet hasn't been searched properly.
- Confusing "about X" with "is X". A blog post or tutorial about headless rendering is not a renderer.
- Judging alternatives by reputation instead of evidence. "X is the standard" is hearsay; "X has had weekly commits for four years and 3k downstream dependents, Y was created six weeks ago" is a finding. Every comparative sentence should be traceable to a number or a README fact you fetched.
- Mistaking a launch for an institution, or the reverse. Stars per day since creation is the cheapest check; always compute it for the original.
- Dropping the user's language. If they wrote in Chinese, answer in Chinese; repo names and descriptions stay as they are.
